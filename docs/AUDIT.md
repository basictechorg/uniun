# Engineering Audit Log

This is the **technical** companion to `CHANGELOG.md`. `CHANGELOG.md` stays terse and user-facing, following Keep a Changelog conventions — this file is where the actual engineering detail behind each release lives: what was found, what was verified against the real code (not guessed), what broke and why, and what's still open. Each entry maps to one or more `CHANGELOG.md` versions but goes deep where the changelog stays shallow.

Format: one dated section per audit pass, newest first. Each item states what was done, how it was verified, and — where relevant — what's still outstanding.

**Gana per-agent UNIUN Cloud pin (foreground + background), issue #161 follow-on**
- Context: issue #161 unified the Shiv/Nataraj/Gana model pickers into one `ShivModelPickerSheet`, but at the time Gana's own engine had no code path to cloud inference (`GanaEngine._runOnce` called `AIModelRunner.generateOneShot` directly, bypassing `LlmRepository` entirely), so its picker was shipped local-only (`showCloud: false`). This pass closes that gap on both the foreground and background Gana paths, plus adds the test coverage the rest of this session's Gana/LLM work had none of.
- **`LlmRepository.generateOneShot` gained a per-call `backendOverride`/`modelIdOverride`** (threaded through `LlmDataSource`/`LocalLlmDataSource`/`RemoteLlmDataSource`/`LlmRepositoryImpl`/`GenerateOneShotUseCase`) — additive, default-null, zero behavior change for existing callers (Nataraj, extraction). `LlmRepositoryImpl.generateOneShot` picks the data source directly from `backendOverride` when set, never reading `LlmPreferencesDataSource.activeBackend` in that path — verified by an explicit `verifyNever(() => prefs.activeBackend)` assertion, not just inferred from reading the code.
- **`GanaEntity`/`GanaModel` gained `desiredBackend` (`LlmBackendType?`)** alongside the existing `desiredModelId`. Local pins keep the original "skip if mismatched with the globally active model" gate (switching the on-device model per-call would mean an expensive, disruptive swap of the app's actual active model — not attempted). Cloud pins route through the new override instead, at zero disruption cost since cloud model selection is just an API parameter.
- **`GanaEngine._runOnce`** branches on `desiredBackend`: cloud skips the `FlutterGemma.hasActiveModel()` gate entirely and calls `GenerateOneShotUseCase` with the override; unavailable cloud (not connected, or no model id) skips with a new `GanaSkipReason.cloudUnavailable` and retries next trigger — no fallback to local, per explicit instruction. Cloud output now runs through `LlmTextSanitizer.clean()` (previously only applied to local output — cloud text isn't pre-sanitized, this was a real gap the cloud path would have hit immediately).
- **Background (`gana_workmanager.dart`)**: verified before implementing (not assumed) that this is safely buildable — `GanaWorkmanagerBootstrap.scheduleBackground()` already requires `NetworkType.connected`; `UniunGatewayClient` and `UniunKeyRecoveryCipher` have zero DI dependencies and are constructible directly in the OS-dispatched isolate (no `get_it`, no `FlutterSecureStorage`, matching the isolate's existing constraints). Per explicit instruction, **no re-authentication per background tick** — the already-minted UNIUN Cloud API key is read once from `LlmCredentialsDataSource` in the main isolate at `scheduleBackground()` time and handed to the bg isolate via `inputData`, exactly like `privkeyHex` already is; a rejected/expired key just fails the run and logs it, no retry/backoff logic. `FlutterGemma.initialize()` is skipped entirely when the tick's one due Gana is cloud-pinned, saving the ~9s on-device load for a run that doesn't need it.
- **Test coverage added this pass** (previously zero for any of `LlmRepositoryImpl`, `RemoteLlmDataSource`, `GanaFormBloc`, `ShivModelPickerSheet`, or `GanaEngine`): unit tests for the backend-override dispatch and model-id fallback, a `GanaFormBloc` test proving the cloud pin round-trips load→submit, a `ShivModelPickerSheet` widget test covering both the default global-switch behavior and the override-callback mode, and — most load-bearing — a `GanaEngine` test that runs the REAL engine against a real (temp, on-disk) Isar instance rather than only mocking collaborators, catching exactly the class of bug a fully-mocked engine test would miss.
- **Integration tests** (`integration_test/`, run on a connected device): `gana_cloud_pipeline_test.dart` hits the real `api.uniun.in` gateway's public catalog (no auth, no side effects) and optionally a real free-model chat completion given an explicitly-supplied throwaway API key. `gana_cloud_engine_e2e_test.dart` goes further — bootstraps the real DI graph (`configureDependencies()`), seeds a real cloud-pinned standalone Gana into the real on-device Isar, and runs the real `GanaEngine`; SKIPs cleanly (not fail) if the device has no active identity or no connected cloud account, and cleans up the local Gana/run/note/queue rows afterward.
  - **Ran this on a real device (vivo 1933, Android 11) and caught a real gap in the test's first draft, not just in the app**: the first run reported "PUBLISHED" and passed, but the user could not find the note anywhere in the app. Root cause — `GatewayBootstrap.start()` (the Gateway sync isolate that actually opens the relay WebSocket and sends) is normally spawned by `HomePage`, which an integration test that only calls `configureDependencies()` never mounts. The publish use case had genuinely written the local `NoteModel` + `EventQueueModel` rows correctly; nothing ever picked the queue row up and sent it over the wire — the test's own local-Isar cleanup then deleted the evidence, making it look like nothing had happened at all. Fixed by calling `GatewayBootstrap.start()` explicitly in the test and waiting for `EventQueueModel.sentCount > 0` (a real relay `OK` ack, per `OutboundPump._onOk`) before calling it published — failing loudly (not silently passing) if no ack arrives within 30s.
  - **Re-ran on the same device after the fix — confirmed a genuine end-to-end pass**: cloud inference via `gemma-4-31b-it` (~8.6s, replied "OK" per the test's prompt), local publish, Gateway isolate connect, and a real relay `OK` ack, all in one run (`OK: cloud Gana published + relay-acked eventId=...`).
  - **Accepted, not hidden, side effect**: on success this publishes one real, permanent Kind-1 note to the connected identity's real feed via the real relay — UNIUN has no delete (Feed Freedom, NIP-09 permanently excluded), so the relay-side event outlives the local cleanup. Explicitly authorized for this session's test identity; anyone re-running it should use a disposable account, not a primary one.
  - **Background (`gana_workmanager.dart`) — now verified live, via a real device, real WorkManager job**: backgrounding the signed-in app registers a job (`adb shell dumpsys jobscheduler | grep -A8 in.uniun.app` to find the id); forcing it with `adb shell cmd jobscheduler run -f in.uniun.app <job-id>` while tailing `adb logcat | grep '\[gana\]'` triggers the real dispatcher. First forced run was cancelled mid-flight (`WorkerStoppedException`) because the app was brought back to foreground while the cloud call was in progress — `GanaWorkmanagerBootstrap.cancelBackground()` fires on `AppLifecycleState.resumed` by design ("the foreground engine takes over"), which is correct behavior, not a bug. Left alone on a second forced run, the tick ran to full completion (`Worker result SUCCESS`) and, on a subsequent trigger, a real cloud-backed Gana ("motivation," no explicit pin) successfully generated and published a note from the killed-app path — confirming the whole chain end-to-end: `inputData` handoff (pubkey/privkey/API key) → global-backend resolution → skip-local-init → real ~30s cloud HTTP round trip → sanitize → publish → clean tick exit.
  - **Found live, only reachable this way**: the global-backend-follow fix (see below) initially shipped foreground-only; testing it in the background isolate surfaced that `gana_workmanager.dart` needed the identical resolution logic duplicated there (no DI, so re-implemented as a free function `ganaResolvesToCloud` + a direct, non-DI `LlmPreferencesDataSource` read) — this would not have been caught without an actual forced background run, since nothing in `test/` exercises this file.

**Unpinned Ganas now follow the global active backend instead of always assuming local**
- User-reported gap: a Gana with no `desiredBackend`/`desiredModelId` pin at all ("use whichever is active") always tried the on-device model, even when the user's actual globally active backend (the same switch Shiv chat uses) was UNIUN Cloud — silently skipping with `noActiveModel` instead of using cloud.
- Fixed in both isolates. `GanaEngine` (foreground) gained one new dependency, `GetActiveLlmModelUseCase` — when a Gana has no pin, it asks that use case what's globally active; if the answer is a cloud model, it routes through the same `GenerateOneShotUseCase` backend-override path as an explicit cloud pin, using the globally active cloud model id. `gana_workmanager.dart` (background, no DI) got the same three-way resolution via a plain function (`ganaResolvesToCloud`) reading a directly-constructed `LlmPreferencesDataSource` — no `get_it`, consistent with the isolate's existing no-DI pattern.
- Three-way precedence, preserved intentionally: (1) explicit cloud pin — unchanged; (2) explicit legacy local pin (`desiredModelId` set, `desiredBackend` null) — unchanged, still skip-on-mismatch against the local active model, verified by a dedicated test asserting it does NOT get silently pulled onto cloud just because the global switch is cloud; (3) fully unset — new, follows the global switch in either direction (verified both ways: global=cloud routes through cloud, global=local hits the identical pre-existing local gate).
- Test coverage: 3 new `GanaEngine` unit tests (14 total now) covering all three cases above. `gana_workmanager.dart` itself has no unit coverage (same pre-existing, structural limitation as the rest of that file) — the live device run above is what actually verified this half of the fix.

**Shiv chat: empty conversations no longer persisted, issue #159**
- Root cause: `ShivAIBloc._onCreateConversation` called `CreateConversationUseCase` (an unconditional Isar `put`) the instant the user opened the "Ask" card or tapped the drawer's "+" — before any message existed. `ShivRepositoryImpl.getConversations()`/the drawer list have no filter on message count, so every abandoned empty chat showed up permanently in history.
- Fixed by deferring persistence: `_onCreateConversation` now only builds an in-memory `ShivConversationEntity` draft (a fresh UUID, title `"New conversation"`) and sets it as `activeConversation` — it's never added to `state.conversations`, so it never appears in the drawer, and no Isar row is written. `_onSendMessage` detects a draft (`activeConversation.conversationId` absent from `state.conversations`) on the first send and calls `CreateConversationUseCase` at that point, using the message text as the title directly (replacing the old separate auto-title-after-save step for that path). Abandoning a draft (navigating away / closing) leaves nothing behind since nothing was ever written.
- `_onCreateConversationSeeded` (Nataraj's "discuss" action) needed no change — it already always follows creation with an immediate `_onSendMessage`, so it now naturally persists through the same lazy path.
- Test coverage added (`test/features/shiv/chat/bloc/shiv_ai_bloc_test.dart`, new file, 0 prior coverage of this bloc's create/send flow): draft-only creation never calls the persistence use case; guarded-by-no-model create is a no-op; first send on a draft persists exactly once with the message-derived title; a second send on an already-persisted conversation does not re-persist; whitespace-only first message stays a no-op draft; send with no active conversation is a no-op; a persistence failure on first send surfaces an error and never saves a message; seeded creation persists via the same lazy path.

**Shiv chat: leaving mid-generation no longer leaves a permanently blank assistant bubble**
- User-reported gap, found by reasoning about issue #159's neighborhood: on send, `_onSendMessage` immediately persists BOTH the user message and an empty assistant placeholder to Isar, then fills the placeholder in as tokens stream. The explicit Stop button (`_onStopStreaming`) already finalized whatever had streamed so far (or `"(stopped)"` if nothing had arrived yet) — but leaving the chat mid-stream (back button, navigating away — `_onCloseConversation`) or tearing down the bloc mid-stream (`close()`, e.g. logout) just cancelled the stream subscription and reset state, **never** writing anything into the placeholder. That row stayed empty in Isar forever; reopening the conversation showed the user's question with a permanently blank reply.
- Compared against how cloud chatbot apps (ChatGPT, Claude) handle this: they don't have this failure mode at all, since generation runs server-side and continues even after the client navigates away or closes the tab — reopening later shows the completed answer. That path doesn't exist for on-device inference (generation genuinely stops the moment the app backgrounds), so the correct on-device pattern is the one our own Stop button already implements: persist whatever was generated, never leave a silent blank.
- Fix: extracted `_persistInterruptedStream(fallbackText)` out of `_onStopStreaming` — writes the sanitized partial content (or `fallbackText` if nothing streamed yet) into the in-flight assistant message via `UpdateMessageContentUseCase`. Wired into `_onCloseConversation` (fallback `"(interrupted)"`) and bloc `close()` (same fallback) ahead of their existing stream-teardown logic, gated on `state.status == ShivChatStatus.streaming` so an idle close never calls it.
- **Test coverage added** (`test/features/shiv/chat/bloc/shiv_ai_bloc_test.dart`, +6 tests, 14 total now): Stop persists real partial tokens; Stop with zero tokens persists `"(stopped)"`; closing mid-stream with zero tokens persists `"(interrupted)"`; closing mid-stream after tokens arrived persists those tokens (not the fallback); closing an idle conversation never calls `updateMessageContent` at all; a stream error surfaces in `state.errorMessage` AND is persisted into the bubble (the existing `_onStreamError` path — previously untested).
- **Test-infra gotcha hit and fixed while writing these**: a `group`-level `tearDown(() => tokenController.close())` on a plain (non-broadcast) `StreamController` hung one test for the full 30s timeout — `.close()`'s returned future only completes once the close event is actually delivered to a subscriber, and the "idle, never sent a message" test never listened to the controller at all, so the future never resolved. Fixed by making the close fire-and-forget (`unawaited(tokenController.close())`) instead of awaiting it in `tearDown`.

### Dependency bump: flutter_gemma 1.2.0 → 1.5.1

- Also bumped: `flutter_gemma_litertlm` 1.0.2 → 1.3.1, `flutter_gemma_mediapipe` → 1.0.4, `flutter_gemma_embeddings` → 1.0.4.
- Rationale researched from real changelogs before bumping (not assumed): litertlm 1.0.3 fixed ANR + heap corruption on multimodal model conversation creation; 1.0.4 fixed a use-after-free crash on stream closure; 1.1.0 improved Android GPU prefill smoothness; 1.2.0 fixed GPU output corruption on Xclipse (Samsung Exynos) devices. None of this required app-code changes — `InferenceChat`/`TextResponse`/`generateChatResponseAsync` API surface is unchanged in 1.5.1.
- **Broke the Android build**: `flutter_gemma` 1.5.1 pulls `background_downloader ^9.5.6` transitively; the resolved `9.5.7` fails to compile on this project's legacy (non-`builtInKotlin`) Gradle setup with `Unresolved reference 'ParallelDownloadTaskRunner'` and similar errors in `BDPlugin.kt`. Root-caused by testing 9.5.4 (pre-bump, worked), 9.5.6, and 9.5.7 — 9.5.6 and 9.5.7 both failed identically, ruling out a version-specific regression theory and pointing at a genuine incompatibility with this project's Kotlin/Gradle toolchain rather than staleness. Pinned via `dependency_overrides: background_downloader: 9.5.6` (can't pin lower — `flutter_gemma` 1.5.1 requires `^9.5.6` and calls its newer APIs).
- Investigated a suspected JDK mismatch (the local shell's `java -version` reported a JDK 26 preview) as a possible root cause — ruled out by `flutter doctor -v`, which confirmed Flutter's actual Gradle invocation uses the bundled Android Studio JDK 21, not the JDK on `$PATH`.
- **Verification gap, documented not hidden**: I could not run a real `flutter run`/Gradle build myself in this environment. The fix was verified by the user actually running the build after each change; the first pin attempt (9.5.4, then a duplicate-key YAML mistake) failed and was corrected based on the user's real build output, not assumed to work.

## How to keep this file useful

- Add an entry here for anything with real technical weight behind it: a root-caused bug, a dependency decision with a rejected alternative, a verification gap that's real and worth knowing about, a discovery that contradicts existing docs.
- Don't duplicate `CHANGELOG.md` — if there's nothing more to say than what the changelog already says, it doesn't need an entry here.
- Be honest about what wasn't verified, not just what was — a gap flagged here is more useful than a claim that turns out to be wrong later.
